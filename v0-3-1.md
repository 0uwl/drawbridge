# Drawbridge v0.3.1: Bootstrap Container, Fixed ZTP Script, Allowlist Editing, Kea Logs

## Context

Continuing v0.3.0's move to a multi-container Podman pod, this release adds a
third pod member and removes a piece of surface area that never did what it
looked like it did.

**Bootstrap container.** DHCP Option 67's `boot-file-name` fetch happens
before any ZTP script code has run on the device, so there's no way to
pre-establish trust for a self-signed cert ahead of it — confirmed against
real C9200CX hardware, where `copy https://...` either blocks on an
interactive accept/reject prompt (nothing to answer it) or fails outright.
Rather than accept that as an open risk, this release adds `drawbridge-bootstrap`:
a third container in the pod, built from `busybox:musl` running nothing but
busybox's `httpd` applet, whose only job is serving the ZTP script over plain
HTTP on port 8090 — a deliberately non-TLS endpoint for the one fetch that
structurally can't use TLS. Everything the script does afterward (phone-home,
completion callback, log push, file downloads) is unaffected and still goes
over HTTPS against the main `drawbridge` container.

**Removing per-device script selection.** `Device.script`, the
`default_script` setting, and the `/files/scripts/*` upload API let an
operator pick a different ZTP script per device — but Kea's Option 67 has
always hardcoded the delivered filename to `ztp-base.py`, and the script
itself never reads a "next script" field to chain-fetch anything else. No
matter what an admin uploaded under a different name, devices only ever
fetched whatever was literally named `ztp-base.py`. This release removes
that entire dead surface and replaces it with a single fixed script, baked
directly into the `drawbridge-bootstrap` image at build time — versioned
with the release, no host file management, and no ownership race between
`drawbridge` and `drawbridge-bootstrap` starting in either order.

**Allowlist editing.** Devices could only ever be added or removed, never
edited — correcting a typo'd MAC or reassigning an image meant deleting and
re-adding the whole entry. `PUT /api/v1/devices/<serial>` closes that gap.

**Missing filenames in the allowlist table.** Investigation found Image and
Config already rendered correctly — the only column that was ever missing
was Script, which disappears along with `Device.script` above rather than
being separately fixed.

**Kea logs.** Kea's own DHCP server logs (lease grants, errors) had no path
into Drawbridge at all — the only way to see them was `tcpdump` or reading
`journalctl` on the host. This release wires Kea's local syslog output
through a second `drawbridge-rsyslog` listener into a new, purpose-built
`KeaLogEntry` table, queryable via `GET /api/v1/kea-logs`. Unlike device
syslog, Kea's own logs have no device/serial to correlate to, so this
deliberately does not reuse `DeviceLogEntry` or its existing `:10514`
listener — a second port keeps the two log sources cleanly separated rather
than adding per-source branching logic to `container/rsyslog-drawbridge.conf`,
which docs/logging.md's existing design deliberately avoids. **GUI placement
for viewing these logs is left open for a follow-up** — this release only
gets the data in and queryable.

## Architecture

Pod `drawbridge` now contains **three** containers, still sharing one network
namespace but no filesystem or container-name DNS:

- **`drawbridge`** (`Containerfile`) — the app itself, unchanged shape.
- **`drawbridge-rsyslog`** (`Containerfile.rsyslog`) — now listens on two
  ports: `:10514` for device syslog (unchanged, `DeviceLogEntry`) and a new
  `:10515` for Kea's forwarded syslog (`KeaLogEntry`), each with its own
  `omhttp` action posting to its own endpoint.
- **`drawbridge-bootstrap`** (`Containerfile.bootstrap`, new) — busybox:musl,
  `ztp-base.py` baked in via `COPY` at build time, serves it unauthenticated
  over plain HTTP on `:8090`. No volume mount.

Kea itself remains a native systemd service on the host (not containerized —
rootless Podman can't do the raw DHCP broadcast socket Kea needs), so getting
its logs into the pod needs a host-side hop: Kea logs to local syslog
(`loggers` block, facility `local0`), a new repo-tracked rsyslog rule
(`kea/rsyslog-kea-forward.conf`, installed by `install.sh`) forwards matching
lines to `drawbridge-rsyslog`'s new `:10515` listener.
