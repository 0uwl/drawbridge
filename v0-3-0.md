# Drawbridge v0.3.0: One-Container → Podman Pod

## Context

v0.2.x runs gunicorn, rsyslog, and `log_poller.py` as three s6-overlay-supervised
processes inside one container, with rsyslog writing device syslog to a FIFO that
`log_poller.py` tails and inserts into the DB in-process. s6-overlay was added
solely to supervise those three processes and has caused more operational
headache (env-var stripping requiring `S6_KEEP_ENV=1`, opaque `/init` boot
behavior, a shared "any one dies, kill everything" `finish` script) than the
one-image-to-deploy benefit it bought. This reverts that decision: rsyslog moves
into its own container, in a Podman pod alongside the Drawbridge app container.
s6-overlay and `log_poller.py` are both deleted outright — rsyslog forwards
directly to Drawbridge over HTTP via its `omhttp` module, so each container in
the pod runs exactly one foreground process and needs no supervisor at all;
Quadlet/systemd's per-container `Restart=on-failure` replaces s6's job, with the
added benefit that a crashed rsyslog container no longer takes gunicorn down
with it.

This also adds a new capability along the way: syslog messages that indicate
a device-side lifecycle event (Cisco IOS-XE's "Started install add"/
"Completed install activate"/etc.) update `ProvisioningSession.state` —
filling in state values (`rebooting`, `updating_software`, etc.) that the
model has documented since alpha but that nothing has ever actually set.
This detection lives in Drawbridge itself (`drawbridge/device_events.py`), not
in rsyslog config, specifically because Drawbridge is expected to eventually
handle Juniper ZTP too: a vendor-keyed Python trigger table is unit-testable
per vendor and keeps the "which strings mean what state" knowledge next to
`PROVISIONING_STATES` in one reviewed/tested place, instead of sprawling
`if`/`else if` vendor branches across an ops config that isn't code-reviewed
or tested the same way. rsyslog's job stays reduced to "forward every line as
JSON" — genuinely vendor-agnostic, so adding Juniper support later touches
only `device_events.py`, not the rsyslog container/config at all.

## Architecture

Pod `drawbridge` (Quadlet `.pod` unit) contains two containers:
- **`drawbridge`** — the app image (built from `Containerfile`, now stripped of
  s6/rsyslog entirely), runs `gunicorn` directly as its only process.
- **`drawbridge-rsyslog`** — a new, separate **Alpine**-based image (`apk add
  rsyslog rsyslog-http` — Alpine packages the `omhttp` module as `rsyslog-http`,
  unlike Debian/Ubuntu which don't ship it at all), runs `rsyslogd` directly.

Pod members share a network namespace (not a filesystem or container-name DNS),
so rsyslog reaches Drawbridge at `https://127.0.0.1:8080`. `PublishPort=`
therefore lives on the `.pod` unit, not per-container.

`log_poller.py` and the FIFO disappear completely: rsyslog's `omhttp` module
POSTs every line straight to Drawbridge's existing `POST /api/v1/device-logs`
endpoint — one action, unconditionally, no per-vendor branching in rsyslog at
all. The IP→serial correlation that `log_poller._handle_line` used to do
moves into the `device-logs` Flask route itself, which also now runs each
message through `drawbridge/device_events.py`'s `detect_state()` and updates
the correlated session's state inline when it matches — no separate
`/api/v1/device-events` endpoint, no second HTTP round-trip per event.

## File-by-file changes

**`Containerfile`** — delete the s6-overlay download/install block, drop
`rsyslog` from `apt-get install`, delete `ENV S6_KEEP_ENV=1`, delete the two
`COPY container/...` lines for s6-rc.d/rsyslog conf, replace `ENTRYPOINT
["/init"]` with `ENTRYPOINT ["gunicorn", "drawbridge:create_app()", "-c",
"drawbridge/gunicorn.conf.py"]`, drop the `10514` `EXPOSE` lines.

**`container/s6-rc.d/`** — delete entirely (`gunicorn/`, `rsyslog/`,
`log-poller/`, `user/contents.d/`).

**New `Containerfile.rsyslog`** (repo root, multi-arch like the main one):
```dockerfile
FROM alpine:3.20
RUN adduser -D -u 1000 rsyslog \
    && apk add --no-cache rsyslog rsyslog-omhttp
COPY container/rsyslog-drawbridge.conf /etc/rsyslog.d/drawbridge.conf
USER rsyslog
EXPOSE 10514/udp
EXPOSE 10514/tcp
ENTRYPOINT ["rsyslogd", "-n", "-i", "NONE", "-f", "/etc/rsyslog.d/drawbridge.conf"]
```
Runs non-root — :10514 is unprivileged and there's no FIFO/pidfile to write
root-owned.

**`container/rsyslog-drawbridge.conf`** — rewrite, simpler than earlier drafts
now that vendor parsing moved into Python (see `device_events.py` below).
Drop `ompipe`/FIFO/`workDirectory`; load `omhttp` (+ `omstdout` purely for
visibility via `podman logs drawbridge-rsyslog`). One JSON template using
`option.jsonf="on"` + `property(... format="jsonf")` (proper escaping of
arbitrary `%msg%` content — quotes/backslashes/unicode — instead of
hand-rolled string concatenation), one unconditional action — no `if`/`else
if` chain, no per-vendor branching, no second endpoint:

```
template(name="console" type="string"
         string="%timestamp:::date-rfc3339% %fromhost-ip% %msg%\n")
*.* action(type="omstdout" template="console")

template(name="deviceLogBody" type="list" option.jsonf="on") {
    property(outname="ip" name="fromhost-ip" format="jsonf")
    property(outname="message" name="msg" format="jsonf")
}
*.* action(type="omhttp" name="device-logs" server="127.0.0.1" serverport="8080"
    usehttps="on" tls.cacert="/app/data/tls/cert.pem"
    restpath="api/v1/device-logs" template="deviceLogBody"
    action.resumeretrycount="-1")
```

Adding Juniper (or any future vendor) support touches only
`drawbridge/device_events.py` below — this file never changes again for that.

**`drawbridge/tls.py`** — add a SAN to the generated cert (`127.0.0.1` +
`localhost`) so libcurl-based omhttp's hostname verification passes when
connecting to `https://127.0.0.1:8080`; today's cert is bare-CN with no SAN,
which fails that check even when otherwise trusted. Note in deployment docs:
existing no-SAN certs from upgraded installs need `data/tls/{cert,key}.pem`
deleted and regenerated.

**New `drawbridge/device_events.py`** — plain module (not a Flask
blueprint — no route, no `api/` package), holds the vendor-keyed trigger
tables and one function:

```python
"""Syslog message -> ProvisioningSession state detection. Each vendor gets
its own tuple of (state, keywords) rules, checked in order — first match
wins, so a terminal/specific state (e.g. an error) should sit before a
broader in-progress one within the same vendor's table. Keywords are plain
substrings, matching how these platforms' own logging conventions read (no
regex needed for anything seen so far). Cross-vendor collision isn't a
concern: different platforms' log line vocabularies don't overlap, so
there's no need to detect which vendor a line came from before matching.
"""

# Cisco IOS-XE install/reboot lifecycle - see docs/logging.md.
CISCO_IOS_XE_TRIGGERS = (
    ('rebooting', ('Completed install activate',)),
    ('error', ('OPERATION_ERROR',)),
    ('updating_software', ('Started install add', 'Started install activate')),
)

# Juniper ZTP - add trigger tuples here once wired up; nothing else in this
# codebase needs to change (see docs/logging.md, "Multi-vendor").
JUNIPER_TRIGGERS: tuple = ()

ALL_TRIGGERS = CISCO_IOS_XE_TRIGGERS + JUNIPER_TRIGGERS


def detect_state(message: str) -> str | None:
    """Returns the state a syslog line implies, or None for a routine
    line that isn't a lifecycle event."""
    for state, keywords in ALL_TRIGGERS:
        if any(keyword in message for keyword in keywords):
            return state
    return None
```

Each state returned here is always a member of `PROVISIONING_STATES`
(`models.py`) by construction — both live in Python, reviewed and tested
together, so there's no equivalent of the old rsyslog-config-typo risk to
guard against with a 422 path.

**`drawbridge/api/device_logs.py`** — `POST /device-logs` accepts a second
body shape: `{serial, message}` (existing, source='script') or `{ip,
message}` (new, source='syslog') — the latter does `find_active_session_by_ip`
lookup server-side and tolerates no match (serial stays null), same behavior
`log_poller._handle_line` had. After inserting the `DeviceLogEntry`, it also
calls `device_events.detect_state(message)`; if that returns a state and a
serial was resolved (either given directly, or correlated from `ip`), calls
`update_session_state(session, serial=serial, state=state)`. This subsumes
what would otherwise have been a separate `POST /api/v1/device-events`
endpoint fed by rsyslog.

**`drawbridge/models.py`** — add `PROVISIONING_STATES = frozenset({...})`
promoting the existing comment-only state list into a real validated set,
plus a new `'error'` value (see rsyslog conf above — `OPERATION_ERROR`
detection) alongside the existing six. No new lifecycle handling needed:
`provision_complete` (leases.py) already matches/deletes sessions by
serial+ip regardless of current `state`, so an errored session still resolves
normally whenever the device eventually calls back.

**New `frontend/src/utils/provisioningStates.ts`** — a state→badge-class map
with a fallback, plus a generic label formatter:

```ts
// Session states are produced by drawbridge/device_events.py (Cisco today,
// Juniper planned — see docs/logging.md, "Multi-vendor") and aren't a
// closed set from the frontend's perspective: new vendor states can appear
// without a matching frontend release. Stays a plain Record with a `??`
// fallback, not an exhaustive union — deliberately different from
// TYPE_LABELS (fileTypes.ts), whose FileType union IS closed.
export const STATE_BADGES: Record<string, string> = {
  lease_approved: 'badge-ghost',
  script_fetched: 'badge-info',
  downloading: 'badge-info',
  updating_software: 'badge-warning',
  rebooting: 'badge-warning',
  configuring: 'badge-info',
  error: 'badge-error',
}

export function stateBadgeClass(state: string): string {
  return STATE_BADGES[state] ?? 'badge-neutral'
}

// No state->label map to maintain: unlike badge color (which needs
// explicit intent per state), "snake_case -> Title case" needs none, so
// it already handles any future/unrecognized value for free.
export function formatStateLabel(state: string): string {
  return state.replace(/_/g, ' ').replace(/^\w/, (c) => c.toUpperCase())
}
```

`badge-neutral` isn't a new fallback color — it's already this codebase's
"unrecognized/other" bucket (`DeviceLogs.vue:36` uses it for a non-`'script'`
log source), reused here for the same "no specific treatment" case.

**`frontend/src/views/Sessions.vue`** — use both: `<span class="badge"
:class="stateBadgeClass(s.state)">{{ formatStateLabel(s.state) }}</span>`
instead of the current always-`badge-info`, raw-string `{{ s.state }}`. Single
usage site (session state is rendered nowhere else), so a plain function
matches `Files.vue`'s own inline `statusBadgeClass` pattern — no
`<StateBadge>` component needed for one call site.

**`frontend/src/types.ts`** — `state: string` (line 37) stays a loose string,
not a literal union; update its comment (currently "no code transitions
state [yet]") to explain *why* it stays wide even though real transitions
exist now — new vendor states must render gracefully (via the fallback
above) without requiring a frontend type change in lockstep.

**`drawbridge/queries.py`** — add `update_session_state(session, *, serial,
state)`: looks up via the existing `get_provisioning_session(session,
serial)` (already imported/used in `device_logs.py`), sets `.state` if found,
returns `None` otherwise — same no-commit-inside convention as
`add_device_log_entry`. Takes `serial`, not `ip`, since by the time
`device_logs.py` calls this the serial is already resolved either way (given
directly for `source='script'`, or via `find_active_session_by_ip` for
`source='syslog'`) — no separate ip-based lookup path needed here.

**Quadlet** — replace `quadlet/drawbridge.container` with three files:
- `quadlet/drawbridge.pod` — new `.pod` unit owning `PublishPort=8080:8080` +
  `10514:10514/udp`+`/tcp` and `UserNS=keep-id:uid=1000,gid=1000`.
- `quadlet/drawbridge.container` — trimmed (drop `PublishPort=`/`UserNS=`, add
  `Pod=drawbridge.pod`), otherwise unchanged (`Volume=`, `Environment=`,
  `ReadOnly=true`, `Tmpfs=`).
- `quadlet/drawbridge-rsyslog.container` — new: `Pod=drawbridge.pod`,
  read-only `Volume=%h/.local/share/drawbridge/data:/app/data:ro,Z` (just for
  the TLS cert), `ReadOnly=true`, `Tmpfs=/tmp`, `Restart=on-failure`.

`systemctl --user start drawbridge` becomes `systemctl --user start
drawbridge-pod.service` (starting the pod starts both member containers).

**`install.sh`** — fetch/install three quadlet files instead of one (loop over
the existing install-or-backup block rather than tripling it); pull two
images; update the final start command.

**`.github/workflows/ci.yml`** — add `Containerfile.rsyslog` to the backend
path filter and the `dockerfile-roast` lint glob; `publish` job builds+pushes
both images (`ghcr.io/<repo>:latest` and `ghcr.io/<repo>-rsyslog:latest`).

**Docs** — `docs/logging.md`: rewrite the "in-container rsyslog, not a
sidecar" decision (now reversed) and the "Container layer"/"Why a named pipe"
sections for the pod+HTTP design; add a "Multi-vendor" note explaining that
`device_events.py` is where Juniper support gets added later, and that
rsyslog config itself is vendor-agnostic and shouldn't need to change for it.
`docs/deployment.md`: Container section (two images, pod+2-unit Quadlet — no
third container for events, since there's no separate endpoint — updated
smoke test), TLS section (SAN note). `docs/api.md`: add the (currently
undocumented) `device-logs` routes — no new route to document beyond that,
since `/api/v1/device-events` no longer exists.

**Tests** — delete `tests/test_log_poller.py`. Add
`tests/test_device_events.py`: pure unit tests for `detect_state()` (each
Cisco trigger string returns its expected state; an unrelated line returns
`None`) — no Flask/DB fixtures needed, following the same "test the logic in
isolation" split `test_log_poller.py` used for `_handle_line`. Extend the
existing device-logs API test file with: the `{ip, message}` body shape
(known-ip persists `source='syslog'`+correct serial, unknown-ip persists
`serial=None`); and a case posting a trigger message (e.g. containing
"Completed install activate") and asserting the correlated session's `state`
updates as a side effect of the same `POST /device-logs` call.

## Verification

- `podman build -f Containerfile .` and `podman build -f Containerfile.rsyslog .`
  both succeed on amd64 (and ideally arm64 via QEMU, matching existing CI).
- `pytest` passes, including the new `test_device_events.py` and extended
  device-logs test cases.
- Manual pod smoke test: bring up the pod, `logger -P 10514 -T "Completed
  install activate"` from another host, confirm a `DeviceLogEntry` row
  appears via `GET /api/v1/device-logs` AND the matching
  `ProvisioningSession.state` becomes `'rebooting'`. Repeat with
  `"OPERATION_ERROR"` to confirm `'error'`.
- `podman logs drawbridge` / `podman logs drawbridge-rsyslog` both show clean
  startup with no supervisor in between.
