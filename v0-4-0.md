# v0.4.0 Implementation Plan

Goal: allowlist entries specify a *desired software version* instead of a
raw image filename; `/api/v1/provision-request` decides whether the device
needs an image push based on what the device already reports; the ZTP
script fetches and applies image/config as instructed, then always cleans
up after itself. Also adds a wildcard `serial='*'` allowlist entry for
directly-connected local deployments.

## 1. Image upload — version parsing

- `drawbridge/models.py`: add `version: Mapped[str | None]` to `ZTPFile`.
  Only meaningful for `file_type='image'`; always `None` for configs.
- Parsing helper (e.g. `drawbridge/files.py`): `parse_version_from_filename()`,
  regex `\d+\.\d+\.\d+`, run against the uploaded filename.
- `POST /files/images`: gains an optional `version` form field, same shape
  as the existing optional `sha256` field —
  - if `version` is supplied, it's used as-is (operator override);
  - else if the filename parses cleanly, use the parsed value;
  - else reject with `422 version_required` and let the frontend prompt for
    manual entry, same UX as the existing checksum-mismatch flow.
- **1:1 enforcement at upload time**: before accepting, check for an
  existing `ZTPFile` row with `file_type='image'` and the same `version`.
  If one exists, don't silently reject or silently replace — the API
  returns `409 version_conflict` (naming the existing filename), and the
  frontend surfaces this as a confirmation prompt: replace the existing
  mapping for that version, or cancel the upload. A replace re-submits the
  same upload with an explicit `replace=true` (or similar) flag so the
  conflict check is bypassed and the old `ZTPFile` row/file is superseded.
- `POST /files/configs` is unaffected — configs have no version concept.
- **`DELETE /files/images/<filename>`**: since a `Device.version` mapping
  to this image's version now becomes unresolvable once it's gone (see
  §4's fail-closed behavior), the frontend must warn before deleting an
  image that's in use — "this version is mapped to N allowlist entries;
  deleting it will invalidate their provisioning until a replacement image
  for that version is uploaded." Needs a way to check usage: either the
  delete endpoint returns the count/list of affected `Device` rows on a
  dry-run/confirm step, or the frontend queries `GET /api/v1/devices` and
  filters by version client-side before confirming.
- Docs: `docs/database.md` (`ZTPFile` schema block + prose), `docs/api.md`
  (`POST /files/images` and `DELETE /files/images/<filename>` rows).

## 2. Allowlist (`Device`) changes

- `drawbridge/models.py`: replace `Device.image` with
  `version: Mapped[str | None]` (desired version, falls back to a new
  `default_version` `Setting` on creation — same fallback pattern
  `image`/`default_image` used today). `config_file` is untouched.
- `POST /api/v1/devices` / `PUT /api/v1/devices/<serial>`: body takes
  `version` instead of `image`. Frontend offers it as a dropdown sourced
  from `GET /files/images` (distinct versions), not free text — so an
  invalid/unknown version can't be submitted from the UI, but the API
  should still validate server-side (`422 unknown_version`) since it's a
  public-ish admin API, not just a UI-enforced constraint.
- **Wildcard entry**: a normal `Device` row with `serial='*'`, `version`,
  and `config_file` set the usual way. No schema change needed — `serial`
  is already the primary key and already a free-text field.
  - Lookup at `provision-request` time: try an exact match on the reported
    serial first; if none, fall back to the `serial='*'` row if it exists.
  - The `ProvisioningSession`/`ProvisioningLog` rows created still use the
    device's *real* reported serial, never `'*'` — the wildcard only
    changes which `Device` row supplies version/config.
  - Frontend: probably a dedicated "Allow all devices" toggle when creating
    an entry (sets `serial` to `'*'` under the hood) rather than expecting
    an operator to type `*` directly — same underlying row either way.
  - `docs/decisions.md`: add an entry documenting this exception to
    "serial number over MAC, canonical allowlist identifier" — same
    treatment as the other accepted-tradeoff entries in that file: what it
    is, why it's safe for the local/directly-connected threat model, why
    it's opt-in per-deployment rather than default.
- Docs: `docs/database.md` (`Device` schema block), `docs/api.md`
  (`/api/v1/devices` rows).

## 3. Frontend (`frontend/src/views/Devices.vue` and related)

- Allowlist table columns: serial, desired version, config file, added
  timestamp, provisioning state only.
- Row click → modal with description, MAC, current version, image
  filename, device model (read-only, sourced from the active
  `ProvisioningSession` if one exists — these fields have no meaning once
  the session is gone, consistent with them never being copied onto
  `Device`). Modal also embeds the live log feed (reuse whatever polls
  `GET /api/v1/device-logs?serial=...` today for the sessions view).
- Image upload form: version field pre-filled from the parsed value,
  editable, blocks submit if empty and unparseable (mirrors the checksum
  field's UX).
- Device create/edit form: version dropdown instead of image-filename
  dropdown.

## 4. `GET /api/v1/provision-request` — expanded contract

- New required query param: `version` (the device's own current version,
  from `show version` — already known locally before this call per
  `_get_device_info()`, so no sequencing problem). Missing → `422
  missing_parameter`, same as a missing `serial` today.
- Lookup: exact `serial` match, else `serial='*'` fallback (see §2).
- Decision logic, evaluated server-side (not "branching" behaviorally, just
  deciding what to include in the response payload):
  - `Device.version` is `None` → no upgrade concept for this device; never
    include `image` in the payload.
  - `Device.version == version` (exact string equality, both `X.X.X`) →
    already correct; don't include `image`.
  - `Device.version != version` → look up the `ZTPFile` row for that
    version and include its filename as `image`.
    - If no matching `ZTPFile` exists (image deleted after the allowlist
      entry was created — see §1's delete-warning note), **fail closed**:
      deny the provisioning request outright rather than silently
      proceeding with config only.
  - `config_file` is included whenever `Device.config_file` is set,
    independent of the version decision (unchanged from current behavior).
- `ProvisioningSession` is still created at approval, still copies
  `image`/`config_file`/`version` from the resolved `Device` row (real
  serial, even for a wildcard match).
- `PUT /api/v1/provision-request/facts` is **unchanged** — it's still the
  only place `model`/current-`version`/`mac` land on the session, called by
  the script after approval, per the existing "facts-first" design. No
  endpoint work needed here beyond what already exists.
- Docs: rewrite the `/api/v1/provision-request` contract section in
  `docs/api.md` with the new query param and expanded response shape.

## 5. ZTP script (`scripts/ztp_script.py`)

- **Error handling**: wrap CLI-invoking calls (`cli.cli`, `cli.execute`,
  `cli.configurep`) in `try/except` against the Guestshell `cli` module's
  own exception type. Nothing in the script catches this today — confirm
  the exact class on real hardware (Cisco's Guestshell docs name it
  `cli.CLIError`) before relying on it. On a fatal error: log the exact
  exception, call `report_complete()`/`report_new_state('error')` with
  detail, then fall through to cleanup — never leave the device in a
  half-configured state with no callback.
- **Fetch + apply image**: if `provision-request`'s response includes
  `image`, `cli.execute(f'copy {DRAWBRIDGE_BASE_URL}/files/images/{image} flash:')`
  (same `copy`-primitive constraint as the existing script fetch), then
  drive the upgrade (`install add file ... activate commit` or equivalent)
  via `cli.configurep`/`cli.execute`, reporting state transitions
  (`updating_software`, `rebooting`) via the existing `report_new_state()`.
- **Fetch + apply config**: if the response includes `config_file`, fetch
  the same way and load it (`copy ... running-config` or `configure
  replace`, TBD which semantics are wanted), reporting `configuring`.
- **Wipe function**: new `wipe_device()`. Removes downloaded image/config
  files from flash, the `status.json` file written for the
  `provision-complete` callback, and reverts the trustpoint config
  installed by `_ensure_c9200cx_trustpoint()` (`no crypto pki trustpoint
  ...`, clear `ip http client secure-trustpoint`). Runs as the literal last
  lines of `main()` — after `report_complete()`, inside a `finally` so it
  still runs on the fatal-error path. Each cleanup step should be
  best-effort and independently caught/logged, so one failed step (e.g. a
  file already gone) doesn't skip the rest.

## 6. Verify on real hardware before relying on

- Exact device-reported version string format from `show version` against
  how uploaded image filenames get parsed — equality matching only works
  if both sides normalize to the same `X.X.X` shape. Flagged by the user
  as a real risk area, not just a hypothetical.
- The Guestshell `cli` module's actual exception class/behavior on a failed
  `configurep`/`execute` call.
- Whether the `copy https://.../files/images/<name> flash:` fetch behaves
  the same for a (typically much larger) image file as it does for the
  script/config fetches already in use.
